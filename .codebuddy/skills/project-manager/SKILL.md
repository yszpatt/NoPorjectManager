# 项目管理看板

## 用途

本 Skill 让 Agent 成为看板的**数据生产者与消费者**：

- 消费：会话开始时读取全局状态与今日计划，知道"现在该做什么"
- 生产：把**思考、决策、下一步计划、版本发布**写回看板，让档案不依赖人工回忆
- 推理：基于「后续计划 + 记录活跃度」推导当日任务，并识别停滞的想法

**这个看板关心什么**：你**想到了什么**、**下一步打算做什么**、**发布了哪个版本**。
**不关心什么**：进度百分比、截止日期、里程碑滑期、排期偏差——它们仍然记录，但退到详情页当辅助信息，也不会产生任何提醒。不要为了"看起来有进展"而虚报进度。

数据以 Markdown 为事实源（可 git diff、可人工编辑）、SQLite 为查询索引，全部落在项目根目录的 `.projectmanager/` 下。

## 写内容的要求（先读这条）

看板的价值全在文字上。写成技术黑话，三个月后连你自己都不想看；写成分条汇报，翻到就能回顾。

**基本形式：结论 + 分条。**

```
看板后台接口与四个视图完成，进入联调
1. 完成：项目、进展、计划、风险的读写接口
2. 完成：四个视图界面与项目详情抽屉
```

四条硬性要求：

1. **首行是结论**：一句话说清这次的结果，能带数字就带。卡片上只显示这一行
2. **下面分条列**：每条以分类标签开头，一条只讲一件事
3. **标签统一**：`完成` / `调整` / `修复` / `决策` / `卡点` / `问题` / `验证` / `下一步`
4. **汇报口吻**：客观、简洁。既不要"聊天"（`顺手` `其实` `一堆`），也不要"开发日志"（文件名、函数名、`feat(x):` 前缀、英文术语）

**禁止**：`优化` / `完善` / `推进` / `对齐` 这类没有宾语的空话；一条里塞多件事；只写做了什么、不写结果与影响。

单条提交、状态变更这类只承载一个事实的，保持一行即可，不用硬拆。

进展 / 卡点 / 下一步计划 / 发布说明 四类的正反例对照、完整标签表与自查清单见 [`references/writing.md`](references/writing.md) —— **每次写入前过一遍**。

### 提交与汇报不要重复

同一件事既 commit 又汇报，看板上就会刷出两行。**一件事只留一条记录**：提交标题已经说清的不再汇报；一组提交构成一件事时汇报一次并带上全部 sha（`refs: { commits: "sha1 sha2" }`）。

**汇报时带上提交 sha 是硬要求。** 看板按 sha 把提交并进汇报——只显示你写的那条，提交以短 sha 徽章挂在旁边。不带 sha 就只能靠时间窗口猜，稍复杂就并不上，于是出现重复。完整边界见 [`references/git.md`](references/git.md)。

## 工具接入

所有能力通过 MCP 服务 `project-manager` 暴露，工具名前缀 `pm_`。注册方式见 `references/registration.md`。

若 MCP 不可用（例如客户端未注册），可用 CLI 兜底，二者写的是同一份数据：

```bash
node bin/pm.mjs summary          # 全局汇总
node bin/pm.mjs brief            # 今日简报
node bin/pm.mjs feed             # 最近都在忙什么
node bin/pm.mjs plan generate    # 生成当日计划
node bin/pm.mjs progress <id> "说明" --source agent   # 兜底写入必须声明来源
node bin/pm.mjs release <id> --version v0.3.2
```

## 核心工作流

### 1. 会话开始：获取上下文（必做）

按代价从低到高，按需选择：

```
pm_get_daily_plan        # 今天的计划（已有则直接用）
pm_generate_daily_plan   # 没有计划时生成，含每条任务的理由
pm_brief                 # 人可读简报：总览 + 滞涨 + 今日计划
pm_get_feed              # 最近都在忙什么（跨项目时间倒序）
pm_summary               # 需要全局量化视图时
```

优先使用 `pm_get_daily_plan`；仅当返回 `status: none` 时才生成。生成后不要自行改写任务标题，用户可能已手工调整过。

### 2. 执行过程中：记录进展

**任何实质进展出现时就记录，不要攒到最后。** 一次调用完成"追加事件 + 修正进度"：`pm_report_progress(id, content, delta | progress)`。

约定：

- `content` 按 [`writing.md`](references/writing.md) 写：**首行结论 + 分条列出**，每条带标签
- 标准的四类记录内容：**做完了什么、做了哪些调整、发现什么卡点与问题**——缺了「卡点/问题」往往是没写全
- **思考、决策、方案取舍**用 `type: "note"`，这类记录是看板主体，不要只记"完成了什么"；阻塞用 `type: "blocker"`，说清卡在哪、需要谁做什么决定
- **已提交的改动必须带 `refs: { commit: "abc1234" }`**（多个用 `commits`）——否则同一件事会显示成两行，见 [`references/git.md`](references/git.md)
- 不要虚报 delta；多条小事合成一条时先问是不是该拆开——**一件事一条**

### 2.5 发布版本：留档

发布了新版本时**必须留档**：`pm_report_release(id, version, note, url)`。`note` 写**这一版用的人能做什么了**，不是改动清单（正反例见 [`writing.md`](references/writing.md)）。

仓库已关联且打了规范版本 tag 时，`pm_sync_git` 会自动采集为发布，不必手工重复记录。自动采集的说明文字来自提交标题，只是原始事实、偏开发视角，值得展开的就补成分条。没有 tag 习惯的阶段就手动记。

### 3. 收尾：闭环当日任务

`pm_complete_daily_task(task_id, note, delta)` 会自动向任务所属项目回写一条进展事件，形成「生成计划 → 执行 → 自动汇报」的闭环，无需再手动调 `pm_report_progress`。

### 4. 维护后续计划（最重要）

**每日计划完全依赖「未完成的路线图项」推导**。没有计划，Agent 只能生成"为 X 写下下一步打算做什么"这类元任务。用 `pm_upsert_roadmap_item(id, title, status)` 维护。

- **`title` 必须是动词开头的具体一件事**：`支持一次导入整个收藏夹` ✓，`优化性能` `完善文档` `推进重构` ✗
- 一条只装一件事，超过 15 个字通常该拆成两条
- **`due` 是可选的**。无日期的计划一样参与推导与展示，不要因为"排不出日期"就不记
- 想清楚下一步后**立刻记下来**，这是这个看板最核心的动作
- 开始做时改为 `status: "in_progress"`（优先展示、优先推导为今日任务）；完成 / 放弃时改为 `done` / `dropped`，不要删除（保留脉络）
- 目标（`pm_upsert_goal`）是次要信息，需要量化指标时才用

### 5. 检查停滞

`pm_check_reminders(stalled_days, min_level)`。只报「计划停滞」：有未完成的后续计划却很久没记录，或活跃项目连计划都没有。用户问"项目怎么样""有什么要处理的"时调用。**不要**去分析进度落后或排期偏差——那不是这个看板的关注点。

### 6. Git 自动采集

`pm_sync_git(project_id?)` 扫描已关联仓库的 commit 与版本 tag，`pm_link_repo(id, path)` 关联本地仓库。

- Git 只贡献**活跃度**（`last_activity_at`、`momentum`），不会擅自改写 `progress`。例外：commit message 里显式声明了 `[pm:项目id] +10`——此时不要再重复调 `pm_report_progress` 累加
- **幂等**：提交事件 id 由完整 sha 派生，重复同步不会产生重复记录
- **提交会并入对应的汇报**；命名规范的 tag 会被采集为发布记录。已被汇报的提交会自动并进去，不要为它再写一条

## 关键约定

细节见 `references/conventions.md`，最容易出错的三条：

1. **优先记「想法与计划」，而不是进度**。没有想法的项目，进度数字毫无意义。
2. **项目 id 是 ASCII 的**。名称含中文时系统会生成随机 id，建议创建时显式传 `id`，便于在 commit message 与 CLI 中引用。
3. **CLI / REST 兜底写入必须声明来源**：`--source agent` 或 `{"source":"agent"}`，否则会被记为「人工」，破坏可追溯性。
